# 文档

本目录放两类东西：**已发布版本的技术档案**，和**跨版本的工程文档**。
计划、报告、实验脚本、参考资料这类过程材料放 `local/`，已被 `.gitignore` 忽略，不随仓库发布。

## 文档地图

| 位置 | 内容 | 读者 |
|---|---|---|
| 仓库根 `README.md` | 产品是什么、能做什么、怎么跑起来 | 第一次来的人 |
| `CHANGELOG.md` | 每个版本面向用户的变更 | 使用者、升级前自查 |
| `docs/versions/vX.Y.Z.md` | 该版本的技术实现：算法、参数、取舍 | 要改 AI 或排查行为的人 |
| `docs/dev/` | 跨版本不变的工程文档：架构、本地开发、部署、UI 约束 | 贡献者 |
| `docs/CREDITS.md` | 素材来源与许可 | 二次使用者、版权方 |
| `docs/local/` | 计划、报告、实验脚本、论文（不入库） | 作者本人 |

## 分层规则

一句话：**README 写「是什么」，docs 写「怎么做」，CHANGELOG 写「变了什么」，local 写「当时怎么想的」。**

- 仓库根的 `README.md` 不写技术内容：不放算法、参数表、性能数字、部署细节、踩坑记录。它只回答「这是什么、能做什么、怎么运行、去哪看细节」。
- 技术内容一律写进 `docs/versions/vX.Y.Z.md` 或 `docs/dev/`，README 只留链接。
- 版本文件**只增不改**。已发布版本的文档冻结；规则变了就写进下一个版本文件，并在开头说明「相对上一版改了什么」。理由是文档必须和当时的代码行为对得上，改旧文档会让读者拿旧结论去读新代码。
- 面向用户的变更同时写进 `CHANGELOG.md`。

## 命名规则

目录与文件名统一 **小写 ASCII + kebab-case**，不用空格、下划线、中文、大写缩写。

| 类型 | 规则 | 例 |
|---|---|---|
| 分类目录 | 复数名词，全小写 | `versions/` `dev/` `plans/` `reports/` `bench/` `ref/` |
| 版本文件 | 一个版本一个 md，`v` + 三段 semver，三段齐全 | `versions/v1.3.0.md`，不是 `v1.3.md` |
| 技术文档 | kebab-case `.md`，不加 `PLAN-` / `REPORT-` 前缀 | `architecture.md` `deploy.md` `ui.md` |
| 带时间的文件 | `YYYYMMDD-slug.md`，日期在前便于排序 | `20261111-engine.md` |
| 脚本与日志 | 以用途开头，序号只在有含义时加 | `perf-legal.mjs` `matches.json` |

文档类型由所在目录表达，不用文件名前缀。`probe-ort2.mjs`、`run2.mjs` 这类无意义序号不再新增；已有的保留，改名收益低于破坏引用。

## 写作密度

版本档案是给改动者看的，不是 CHANGELOG 的复述，也不是实现过程的记录。

- **只写这一版变了的**：不重复上一版没变的实现（模型、推理、部署这些没动就别再抄一遍），不重述 CHANGELOG 的功能清单。
- **只写代码里读不出来的**：参数为什么取这个值、两条路为什么选这条。公式、常量、函数职责以代码为准。
- **不写过程**：怎么发现的、试过什么、哪次调试抓到的，属于 `docs/local/`；档案只留结论。
- **能一句写完就别写一段**。以 1.0.0–1.2.0 为基准（51–72 行），常规版本压在 100 行内；超过就先删一轮，超过 150 行基本可以断定混进了实现过程或功能清单。

## 新增一个版本文件

```bash
touch docs/versions/v1.4.0.md
```

1. 一个版本一个文件，不建子目录。版本内部按主题分节（行为、参数、取舍、代码入口），读者一次滚动就能读完整个版本。
2. 开头写清「相对上一版改了什么、为什么」，不重复上一版没变的实现。
3. 只写结论与机制，不写本机环境：绝对路径、机器配置、实测耗时都不入库。
4. 文件发布后不再改；发现写错，写进下一个版本文件。

## 入库前自查

- 文档里出现的路径必须是仓库内、且被 Git 跟踪的相对路径；说明忽略规则的除外。
- 不出现本机性能实测值、用户名、主机名、盘符路径。
- 新增或改名文档后，检查旧链接是否还有引用（含 `docs/local/` 内的笔记）。
